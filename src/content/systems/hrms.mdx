# Enterprise HRMS Platform

## 1. Problem Statement
Building an HRMS is deceptively complex. On the surface, it looks like simple CRUD: "Employee punches in/out, calculate hours, pay salary."

**Reality:**
- **Attendance accuracy is non-negotiable:** A single missed minute can affect overtime or late deductions, directly impacting payroll.
- **Payroll is high-stakes:** Errors lead to compliance issues, financial loss, and loss of employee trust.
- **Shift rules vary wildly:** Organizations have rotating shifts, grace periods, night shifts crossing midnight, and flexible work arrangements.
- **Scale:** Processing attendance for thousands of employees simultaneously (e.g., 9:00 AM rush) requires robust handling.

---

## 2. System Overview
The system is architected as a hybrid microservices platform leveraging both **ASP.NET Core** and **Node.js** for optimal scalability and performance, with **PostgreSQL** serving as the database source of truth.

- **ASP.NET Core API Microservice**: Handles core domain rules, statutory compliance calculations, identity integrations (OAuth2/JWT + Role-Based Access Control), and the heavy Payroll calculation engines.
- **Node.js Gateway & Real-Time Microservice**: Manages WebSocket connections for chat, routing biometric ingestion streams, and dynamic notification updates.
- **Asynchronous Workflows**: Heavy processing (such as background payroll verification or daily attendance batching) is offloaded using Redis queues.

---

## 3. Attendance & Shift System (DEEP)
This module was the most engineer-intensive part of the platform.

### Hardware Validation & Synchronization
- **Integration**: Directly integrated with Biometric machines and Mobile GPS for field staff.
- **Sync Logic**: A background Node.js service pulls logs from biometric hardware every minute, ensuring near real-time updates.
- **Geo-Fencing**: Mobile punches are validated against allowed office coordinates using PostGIS.

### Shift Definitions & Complexity
We moved beyond simple "9 to 6" logic. The system supports:
- **Grace Periods**: Configurable buffers for late entry (e.g., 15 mins).
- **Cross-day Shifts**: Shifts starting at 10 PM and ending at 6 AM the next day.
- **Auto-Shift Correction**: If an employee swipes in at a time closer to Shift B than Shift A, the system intelligently prompts or auto-corrects.

### Async Processing Strategy
Processing raw punch logs (biometric/web) into meaningful "Attendance Records" (Present/Absent/Half-day) is expensive.
- **Solution**: We decoupled capture from processing.
- Raw punches are written to an immutable `punch_logs` table.
- A background worker picks up unprocessed logs and runs the **Shift Rule Engine**.
- Atomic transactions ensured that updating the attendance status and linking the punch log happened safely.

---

## 4. Security & Compliance
Security is integrated at the core, not an afterthought.
- **Authentication**: Implemented **OAuth2** for secure access delegation and **JWT** for session management.
- **RBAC**: Fine-grained Permission system (e.g., `can_view_salary`, `can_approve_leave`) enforced via ASP.NET Core custom authorization policies and middleware.
- **Audit Trails**: All sensitive actions (e.g., changing an employee's salary) are logged for compliance.

---

## 5. Payroll System (DEEP)
The payroll processing engine is built as a high-performance **ASP.NET Core worker service** in C#. Payroll is modeled as a deterministic state machine to ensure exact calculations and audit trails.

### Core Architecture
- **Salary Structures**: Deserialized JSON structures mapped to custom class hierarchies in C# supporting dynamically compiled arithmetic formulas for tax components, deductions, and statutory compliance (PF, ESIC, PT).
- **Domain Flow**: `Attendance Summary` (Total Present Days, LOPs) -> `ASP.NET Core Payroll Engine` -> `Calculated Payslip`.

### Concurrency & Consistency
- **Thread Pool Tuning**: Running calculations for 15,000+ employees concurrently required tuning the CLR thread pool configurations to prevent thread starvation under heavy lock contention.
- **Transactional Consistency**: Leveraged **EF Core Database Transactions** (`BeginTransactionAsync`) at a Serializable isolation level to guarantee employee salary profiles or attendance logs were not edited mid-calculation.
- **Variance Audits**: Before archiving, the service executes a parallel LINQ query (`PLINQ`) comparing current-month generated slips against the historical record (flagging net adjustments >10% for manual audit).

## 6. Database & ORM Strategy (EF Core + Node.js ORMs)
Given our microservices split, we adapted our data access layers to the specific service characteristics.

### 1. EF Core (The Enterprise Engine)
The C# microservices utilize **Entity Framework Core** to map domain models to PostgreSQL.
- **DbContext Pooling**: Configured DbContext pooling (`AddDbContextPool`) to recycle context objects, reducing GC cycles during query-heavy periods.
- **AsNoTracking**: Read-only APIs for payroll audits are queried with `.AsNoTracking()` to avoid tracking state overhead, improving response speed by ~35%.
- **Raw SQL execution**: Complex reporting queries are offloaded using parameterized `.FromSqlRaw()` statements, avoiding LINQ compile plan cache misses.

### 2. Node.js ORM Evolution (Sequelize to Drizzle)
The Node.js real-time service evolved from Sequelize to Drizzle.
- **Phase 1 (Sequelize)**: Handled basic biometrics logging and event schemas.
- **Phase 2 (Drizzle ORM)**: Migrated read-heavy chat logs and biometrics queues to Drizzle.
- **Performance**: Latency dropped by 40-60% due to zero object hydration overhead.

## 7. Internal One-to-One Chat System
Integrated directly into the HRMS to secure internal communication.

- **Architecture**: Hybrid WebSocket + REST.
- **Storage**: Chat messages are durable (PostgreSQL). We refrained from using MongoDB to reduce infrastructure complexity, leveraging Postgres's JSONB and partial indexing for performance.
- **Delivery**: We implemented an "Ack" system. If a user is offline, the message is stored as "Pending" and delivered upon reconnection.

---

## 8. Frontend Engineering
The interface focuses on data density and correctness.

- **Complex Dashboards**: Managers view real-time attendance of hundreds of reportees. We implemented **virtualized tables** to handle 5000+ rows without lag.
- **Payroll Wizards**: A multi-step form state machine for running payroll (Select Employees -> Verify Attendance -> process -> Check Variance -> Finalize).
- **Role-Based Access Control (RBAC)**: The frontend logic heavily relies on a central permission hook to conditionally render UI elements (e.g., "Approve Leave" button only for Managers).

---

## 9. Failure Handling & Guarantees
- **Idempotency**: Attendance punch APIs use a unique request ID (or biometric device ID + timestamp) to prevent duplicate entries from shaky networks.
- **Payroll Safety**: We use database-level constraints (composite unique keys) to strictly prevent generating two payslips for the same month.
- **Graceful Degradation**: If the biometric sync service fails, the web attendance portal remains operational.

---

## 10. What I’d Improve at 10× Scale
- **Read Replicas**: Separate read traffic for dashboards to a dedicated replica.
- **Partitioning**: Partition `attendance_logs` and `chat_messages` by month/year to keep index sizes manageable.
- **Dedicated Payroll Pipeline**: Move payroll processing to a completely separate microservice with its own dedicated compute resources.
